# M3 — Add observability

## Goal & exit criterion

See `SPEC.md`, Milestones, M3. Do not copy the bullets here; they go stale.

**Exit criterion:** Done when one game's trace in Langfuse shows a span for every model call, corpus lookup, and program node, and the model spans carry latency, token count, and attempt number.

- **Real:** a self-hosted Langfuse that starts from files in the repo, the game wired to it so that one game is one trace and one batch is one session, every model call and corpus lookup and program node a span, the model spans carrying latency, token count, and attempt number, ending in one live V2 game whose trace is recorded here.
- **Absent:** no variant argument, toggles, or JSONL record (M4); no model, temperature, or thinking decisions (M5); no memory or node H (M6); no batch script, so no health check before each game and no session of forty games (M7); no evaluation, scoring, or prompt management in Langfuse, which `SPEC.md` never asks for.

## How to use these tickets

T1 → T2 → T3 → T4, strictly in order: T1 puts the Langfuse stack and the client library in place, T2 wires the game to it, T3 puts the per-call values on the spans, and T4 is the live game that closes the milestone. T1 and T4 are accepted by the record they leave, so their Acceptance holds once the record commit has landed after the implementation commit, and Status becomes done after the audit (`CLAUDE.md`, Milestones and tickets); T2 and T3 by tests with scripted model outputs and an in-memory span exporter, so neither needs a running Langfuse or Ollama. One ticket, one commit; the T1 and T4 records written into this file, Status updates, audit fixes, and the `DECISIONS.md` entry after a spec change are their own small commits. The measured facts behind these tickets are in `docs/DECISIONS.md`, 2026-10-23 (Langfuse 4.69.0 and Python SDK 5.0.4 on this machine under OrbStack: about 1.7 GiB idle, every value in the exit criterion ingested in a smoke test, spans dropped for good when the stack is down).

### T3 — Latency, token count, and attempt number on every model-call span
- **Status:** todo
- **Produces:** the `config["metadata"]` on every wrapper call in `llm.py` and on every tool invocation in `guesser.py`, so each generation span carries the role, the attempt number, and the kind of call (text, structured, tools), and each tool span carries the round, the call index, and the lookup index; `tests/test_llm.py` and `tests/test_guesser.py` extended; `tests/test_tracing.py` extended.
- **Consumes:** `tracing.py` and the in-memory exporter test setup from T2; the wrapper (`call_text`, `call_structured`, `call_tools`) and `Reply` from M2's `llm.py`; `_tool_loop` from M2's `guesser.py`.
- **Detail:**
  - From BACKLOG M3.2, split: the code here, its Done when in T4. `SPEC.md` M3; [R26]; [R43].
  - Token counts and latency need no code: the callback handler reads the `usage_metadata` of the `AIMessage` the wrapper already gets from `langchain-ollama`, the same counts the wrapper puts in `Reply`, and the span's duration is its latency. What this ticket adds is the metadata the handler cannot know: the attempt number [R26], which the caller computes, and the role, which the handler sees only as the model tag.
  - `llm.py`: `_request` passes `config={"metadata": {...}}` to `invoke`, with `role` (the `ModelSettings.role`), `attempt`, and `kind` (`text`, `structured`, or `tools`; not `call`, which the tool loop uses for its call index); the three `call_*` functions hand their `attempt` through to it. The wrapper's contract (one request, no retry, `LLMError` on failure) does not change.
  - `guesser.py`: `_tool_loop` passes `config={"metadata": {"round": ..., "call": call_index, "lookup": count + 1}}` to `tool.invoke`, so one run of the search tool is one tool span carrying the `(round, call)` key of its `Lookup` entry in State and, as `lookup`, the round's lookup counter after it [R43] (`count + 1` at the point of the call), which with the round identifies one `Lookup` entry: the entries of a round sit in State in counter order. A call that names an unknown tool counts as a lookup in State [R43] but never runs the tool, so it has no tool span; it is listed in T4's inventory from State as such (Q3). A call whose arguments the tool's schema rejects runs the tool (`SPEC.md` Recovery, forks, and replay, Model errors), so it has a tool span whose output is the validation message. The tool runs in node E's code after `call_tools` has returned, so its span is a sibling of the generation span under E's chain span, not its child; to join the two, the generation span of a tool-bound call carries the same `round` and `call` (the three `call_*` functions take an optional `metadata` mapping merged into the config metadata, and `_tool_loop` passes `{"round": ..., "call": call_index}`). The tool span carries no latency or token count of its own: those are on the generation span with the same `(round, call)`, the one reply that made the call.
  - Events that State does not keep but the exit criterion needs as spans, each tested with scripted outputs: a description sent back once [R11] gives two generation spans for B with attempt 1 and 2; a Challenger re-ask [R40] gives two for D with attempt 1 and 2; a question re-asked once [R17] gives two structured spans for E with attempt 1 and 2; a tool-bound reply with no tool call gives a generation span and no tool span; a reply with two tool calls gives one generation span and two tool spans with `lookup` 1 and 2 (the round's counter); a sixth lookup gives no tool span [R43]; a call naming an unknown tool gives a generation span and no tool span; a call the schema rejects gives a tool span whose output is the validation message.
  - Matching the wrapper's output: in the in-memory exporter tests, each generation span's input and output token attributes equal the `Reply`'s counts (the scripted `AIMessage` carries `usage_metadata`), and the span's duration is within 0.1 s of the `Reply.latency` measured around the same `invoke`. The exact attribute keys are the SDK's; the test reads them from the exported spans, not from the SDK's internals.
- **Acceptance:** `uv run pytest tests/test_llm.py tests/test_guesser.py tests/test_tracing.py` passes with the scripted cases listed in Detail; `uv run ruff check .` and `uv run mypy` exit 0; the full `uv run pytest` is green at the commit.
- **Out of scope:** the live run (T4); changing what State records (M4's JSONL decides that); the variant on the spans (M4); cost, prompts, or scores in Langfuse; any change to the attempt-number rules of M2's nodes.
- **Depends on:** T2

## Open questions for the author

Q1, Q2, and Q3 were answered by the author in chat on 2026-10-25: Q1, no `--session` parameter, the session id stays derived from the output directory; Q2, the one-game command runs untraced when the keys are missing or wrong, and the health check waits for M7; Q3, the narrower reading stands, no span made by hand for an unknown-name call. No `SPEC.md` change follows from any of them.

- **Q1** (T2, 2026-10-23; not blocking): `SPEC.md` Implementation (Commands) lists the one-game command's parameters, and a session or batch id is not among them. T2 derives the session id from the output file's parent directory name, which costs no parameter and matches M7's layout (records next to the manifest). If the author prefers an explicit `--session` parameter, that is a `SPEC.md` change to Implementation (Commands) before T2 is dispatched. Either way, M4's JSONL record ticket must keep the output path a file inside the batch's directory, or the session id changes meaning.
- **Q2** (T2, 2026-10-23; not blocking): when the Langfuse keys are missing or wrong, T2 lets the game run untraced, with the SDK's warning when the keys are missing or the exporter's logged failures when they are wrong, because `SPEC.md` places the health check in M7's batch script and says nothing about the one-game command. If the author wants the one-game command itself to refuse to run untraced, that is a `SPEC.md` change to Implementation (Commands) or Recovery, forks, and replay.
- **Q3** (T3, T4, 2026-10-25; not blocking): a tool call that names a tool other than the search tool counts as one lookup [R43] and gets a `Lookup` entry in State, but the search tool never runs, so the callback handler makes no tool span for it. T4 reads the exit criterion's "a span for every corpus lookup" as every run of the search tool and lists such an entry with no span. If the author wants the literal reading, T3 adds a span made by hand for that case.
