- **Real:** the three model tags, the one temperature, and thinking on or off for the Describer and the Guesser, each decided by the author on live games recorded here, rerun until a full pass changes none of them; the four batch manifests carrying them with the Ollama server version and num_ctx; the batch time worked out from the settled thinking.
- **Absent:** no prompt tuning, which is the author's (a prompt edit found wanting here is the author's `prompts(<role>)` commit, not a ticket); no change to the residency arrangement in `SPEC.md` Implementation (Models) unless the author edits it after T3 (Q1); no memory, node H, or V3 (M6); no batch script, no metrics, and no reading of a manifest by `play-game` (M7); no request timeout (M4's Q2).

## How to use these tickets

T1 → T2 → T3 → T4 → T5, strictly in order, then T6 and T7 beside each other after T5: every live run after T1 uses the thinking T1 settled, T2 comes before T3 so a prompt edit the author makes from reading T2's game is in place for T3's games, T4 reads T1–T3's games, T5 applies and reruns whatever T1–T4 changed, T6 writes what T5 settled into the manifests, and T7 works out the batch time from it. T1–T4 are run-and-decide tickets: a dispatched agent runs the games and writes the record into the ticket's Detail, the author reads the record and makes the decision, and the decision is written on the ticket's Decision line; each is accepted by the record and the filled Decision line, never by who won or by the quality of the games (`docs/tasks/TEMPLATE.md`, Field rules). T1–T4 touch no code: every code change a decision implies (a model tag, the temperature, a thinking mapping) lands in T5, one commit per changed setting, so a decision ticket is a Markdown-only commit with no code gate (`CLAUDE.md`, Commit workflow). T5 is the rerun loop of `SPEC.md` M5: when pass 1 (T1–T4) changed nothing, T5 records that pass 1 is the full pass that changed nothing and is Markdown-only; otherwise it applies the changes, reruns M2's checks for a changed model, and reruns the four checks as pass 2, 3, … until a pass changes nothing. T6 then writes the settled values into the manifests and T7 the batch time into this file. One ticket, one commit, with the exceptions a live ticket has had since M2: each run's record is its own commit when the ticket makes several runs (T1, T3, T5), the Decision line goes in its own docs commit once the author has decided, and Status updates and audit fixes are their own small commits; Status becomes done only after the audit closes.

Live runs: the Ollama server is a shell server started before T1's first run with `OLLAMA_MAX_LOADED_MODELS=3 ollama serve`, its log redirected to `runs/m5/ollama-server.log`, the menu-bar app quit; a restart during the milestone is noted in the record of the run that follows it, since loads and evictions are read from that log. Every record file goes under `runs/m5-t<n>/` (git-ignored), one file per run named by variant and run number (`v1-run1.jsonl`, with the stderr beside it as `v1-run1.stderr`); the directory name is the Langfuse session id (`tracing.session_id`). The records of M4's three games are in `docs/tasks/M4-end-to-end.md` T4, and their per-role and per-round token figures in its T5; the files under `runs/m4-t4/` are not committed and serve comparison only. A record file is validated, from the repo root, with `uv run python -c "import json, jsonschema; s = json.load(open('data/records/schema.json')); lines = open('<record file>', encoding='utf-8').read().split('\n'); assert lines[-1] == ''; [jsonschema.validate(json.loads(l), s, cls=jsonschema.Draft202012Validator) for l in lines[:-1]]; print(len(lines) - 1, 'line(s) valid')"`, which splits on `\n` only (M4's T3 F1); "validates against the schema" below means this command printed `1 line(s) valid`. A run stopped by a model error is rerun as a crash (`SPEC.md` Recovery, forks, and replay); a run stopped by a code error is debugged to its root cause and reported as an audit finding of this file against the ticket whose run found it, the fix is its own commit, and the run repeats; every run is recorded, not only the last. A swap of a resident model (M4's Q4) costs a reload and a prefill, not game information, so a latency that includes a load is read with the server log beside it and the record says which calls paid one.
